# Engineering tradeoffs

These are design choices for a development portfolio environment, not universally optimal decisions. The project should be re-evaluated against business criticality, data sensitivity, traffic, compliance obligations, and operational capability before production use.

| Decision | Current choice and business rationale | Limitations | When another choice is appropriate |
| --- | --- | --- | --- |
| ECS Fargate vs EC2 or Kubernetes | Fargate removes host patching/capacity management and keeps a small demo focused on containerized application delivery. | Per-task pricing can be higher at steady scale; less host/kernel control; service still needs deployment and scaling operations. | EC2 can fit predictable high utilization, specialized hosts, or cost optimization with an operations team. Kubernetes can fit a multi-service platform needing its ecosystem and portability, where cluster expertise and control-plane complexity are justified. |
| RDS vs self-managed PostgreSQL | RDS provides managed backups, patching options, monitoring integration, and Secrets Manager-managed master credentials with less operational burden. | Managed-service cost/constraints; current instance is Single-AZ and only one day of backups; application currently uses the master credential. | Self-managed PostgreSQL may be justified for specialized extensions/control or unusual economics only when the team can own HA, patching, backups, restore tests, and on-call response. |
| One NAT vs per-AZ NAT | One shared NAT lowers fixed development expense. | Egress is a single-AZ dependency; cross-AZ egress can add cost and latency; outages can block private task access to AWS APIs. | Use per-AZ NAT for higher availability and AZ-local egress, or VPC endpoints for supported traffic when endpoint cost/security requirements make sense. |
| Single-AZ vs Multi-AZ database | Single-AZ RDS lowers demo cost and is acceptable for disposable non-customer test data. **Operator note:** one-day retention followed a development-account restriction, not a production design choice. | No automatic standby failover; instance/AZ failure interrupts persistence; current `skip_final_snapshot = true` increases data-loss risk on destroy. | Multi-AZ and tested backups/restores are expected when recovery objectives and service commitments require them. Multi-AZ alone is not a backup strategy. |
| Public ALB vs private application workloads | Public ALB is an easy API demonstration entry point; tasks and RDS remain private behind security-group boundaries. | Development listener is HTTP. Credentials/data sent through it are not protected by transport encryption. A public endpoint increases attack surface. | Add ACM-backed HTTPS, redirects, WAF/rate limits, and authentication protections for public services. A private ALB/VPN/PrivateLink can suit internal-only operational tools. |
| Secrets Manager vs hardcoded credentials | Secret ARNs and runtime injection avoid committing database/JWT secrets and centralize secret lifecycle. | Secret retrieval needs correct execution-role and possibly KMS permissions; rotation is not established; application currently receives RDS master credentials. | Use a managed rotation/workload identity design with a least-privilege app DB role; use a different approved secret store only where its security and lifecycle controls are equivalent. |
| IAM task roles vs static AWS keys | ECS task credentials are short-lived and scoped to the role; no application static AWS keys are required. | Incorrect task/execution role separation or broad policies can still grant excess access; effective access also depends on resource/key policies and org controls. | Static keys should generally be avoided for workloads; federation/identity center/assume-role is preferable for people and CI. |
| Managed Bedrock vs self-hosted model | Managed inference avoids operating GPU/model-serving infrastructure; Converse via Boto3 integrates with the ECS task role. | Provider availability, regional/model access, token cost, quotas, data governance, and model behavior remain dependencies. | Self-host when workload economics, data residency/control, latency, or model customization justify the substantial model-serving and patching burden. Evaluate managed alternatives against these same constraints. |
| Read-only AI vs autonomous agent | A recommendation-only assistant can support incident triage without giving a model tools to change infrastructure. This reduces action blast radius. | Engineers must verify advice; no direct telemetry query tools are wired in, so recommendations depend on the prompt supplied. Prompt/output checks are incomplete. | Carefully constrained automation may be appropriate for deterministic, reversible, policy-checked runbooks after approval gates, audit, idempotency, and failure testing—not by giving a model broad AWS permissions. |
| Development cost vs production resilience | Small RDS, one NAT, minimal Fargate resources, seven-day logs, and a mutable `dev` image reduce demo cost and operational complexity. | Lower resilience, retention, observability, and release integrity; resource configuration can fail under production load. | Increase redundancy/retention/compute, immutable releases, alarms, backup recovery, and operational coverage when risk and business impact justify the cost. |

## Cross-cutting tradeoffs

- **Modularity versus abstraction:** Terraform modules reduce duplication and separate infrastructure concerns, but module composition is only reusable when environment-specific values, provider configuration, state, and IAM are externalized. The current provider pins region/profile and only development is evidenced.
- **Managed database credential convenience versus least privilege:** RDS-managed master passwords remove a hardcoded password but do not grant the application least privilege. Use a separate application principal with only required table/schema permissions.
- **Simple HTTP health checks versus useful readiness:** `/api/health` reports process health; `/api/ready` probes PostgreSQL. Separate probes help distinguish application startup from database dependency health, but readiness behavior and load-balancer policy must be deliberately chosen.
- **Mutable tag convenience versus release reproducibility:** `:dev` makes manual pushes simple, but deployments should identify immutable digests and retain rollback artifacts.
- **Regex and prompt controls versus security guarantees:** selected input/output checks are defense-in-depth only. Use data minimization, bounded context, explicit handling, strong auth/rate limits, testing, and human oversight; do not treat prompt text or regex as a complete DLP/security boundary.

## Conditions for a production architecture decision

Before selecting production topology, define business criticality and service objectives; classify data and establish legal/compliance obligations; specify recovery time/point objectives; model failover and restore paths; estimate traffic and AI spend; test identity/secret rotation; and review operational staffing. No architecture label or AWS managed service is itself proof of compliance, availability, or safe financial processing.
